# ИИ-гид музея Фаберже — frontend

Frontend мобильного веб-приложения **«ИИ-гид музея Фаберже»**: Next.js 15
(App Router) + TypeScript + Tailwind v4. В одном приложении две части:

- **посетительская** — залы, витрины и карточки экспонатов, распознавание
  экспоната по фото, чат с ИИ-гидом, озвучка, поиск;
- **админка** (`/admin`) — каталог (залы, витрины, экспонаты, фото) и аналитика
  посетителей.

Всю логику (каталог, распознавание, ответы гида, озвучку, аналитику) держит
backend — [maldandan78/faberge](https://github.com/maldandan78/faberge)
(FastAPI + PostgreSQL 17 в Yandex Cloud). Фронт только показывает данные,
ведёт локальную историю чата и собирает телеметрию.

Этот README — точка входа для нового разработчика: как запустить, что где лежит,
какие решения приняты и почему, и где уже ломалось.

> [!TIP]
> **Первые 15 минут.** Запустите приложение на моках (`NEXT_PUBLIC_USE_MOCKS=true`,
> см. [«Быстрый старт»](#быстрый-старт)) и пройдите сценарий посетителя. Потом
> прочитайте [«Архитектура»](#архитектура) и
> [«Инварианты и подводные камни»](#инварианты-и-подводные-камни). Остальное —
> по мере надобности.

> [!WARNING]
> **Отдельного тестового стенда нет.** Если в `.env.local` стоит адрес прод-API,
> локальный `npm run dev` работает с боевыми данными: правки в админке меняют
> живой каталог, а клики уходят в аналитику музея. Для экспериментов берите
> моки или локальный backend.

## Продукт и основной сценарий

Посетитель сканирует **QR-код** в музее или открывает приложение по ссылке,
выбирает зал, раскрывает витрину, открывает карточку экспоната. Кроме того, он
может **сфотографировать предмет**, получить о нём рассказ гида,
**задать вопрос** в чате и **прослушать** ответ.

```
Главная (/)            → список залов, поиск, «Распознать», «Чат с гидом»
  └ Зал (/halls/N)     → описание (свёрнуто), «Прослушать», витрины секциями
      └ Витрина        → экспонаты по номеру путеводителя
          └ Экспонат   → карточка, «Прослушать», «Спросить гида», похожие
Распознать (/recognize) → камера → снимок → экспонат + «другие варианты»
Чат (/chat)            → рассказ гида о предмете → диалог → подсказки-вопросы
```

Каталог — около 1250 карточек из 12 залов по **путеводителю музея 2014 года**.
Путеводитель считается источником истины: номера залов, витрин и экспонатов в
приложении совпадают с печатными.

## Быстрый старт

Нужны Node.js 20+ и npm (сборка проверена на Node 26).

```bash
npm install
cp .env.example .env.local
npm run dev
```

Откройте http://localhost:3000. В `.env.example` по умолчанию
`NEXT_PUBLIC_USE_MOCKS=true`: приложение работает на фикстурах без backend.

Приложение рассчитано на телефон. На десктопе включайте эмуляцию мобильного
устройства в DevTools. Камера работает только в защищённом контексте:
`localhost` подходит, а IP-адрес в локальной сети по http — нет.

| Команда                           | Что делает                                                  |
| --------------------------------- | ----------------------------------------------------------- |
| `npm run dev`                     | dev-сервер (Turbopack), порт 3000                           |

## Окружение и моки

| Переменная              | Значение                                                                                |
| ----------------------- | --------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_API_URL`   | Базовый URL backend без `/` на конце. Пусто — относительные пути (так работают моки).   |
| `NEXT_PUBLIC_USE_MOCKS` | `true` — поднять MSW и работать на фикстурах; `false` — ходить в `NEXT_PUBLIC_API_URL`. |

Обе переменные `NEXT_PUBLIC_*` встраиваются в бандл **при сборке**. Если вы
поменяли их, пересоберите приложение, одного перезапуска мало.

**Адрес прод-API** в репозиторий не кладём. Его можно взять у команды или в
backend-репозитории (`yaak/`, окружение «Global Variables»). Для работы с
локальным backend поднимите его через `docker compose up --build`
([инструкция](https://github.com/maldandan78/faberge#быстрый-старт)) и укажите
`NEXT_PUBLIC_API_URL=http://localhost:8000`. CORS там по умолчанию открыт (`*`).

### Моки (MSW)

- `mocks/handlers.ts` — обработчики запросов, `mocks/data/` — фикстуры (9 экспонатов,
  12 залов, 18 витрин, отчёты аналитики).
- Воркер (`public/mockServiceWorker.js`) стартует в `app/providers.tsx` только при
  `NEXT_PUBLIC_USE_MOCKS=true`. Модуль моков грузится динамическим импортом и в
  боевой бандл не попадает.
- Пути в обработчиках записаны с wildcard (`*/halls`, `*/exhibits/:id`), поэтому
  они же ловят `/admin/halls`, `/admin/exhibits/:id` и т. п.
- **Моки покрывают не всё.** Загрузки фото экспоната, обложки зала и
  перестановки залов (`PUT /admin/halls/reorder`) в них нет: эти запросы уходят
  мимо MSW и падают. Проверять их можно только на настоящем backend.
- Вход в админку на моках принимает любые логин и пароль.
- Телеметрию MSW тоже перехватывает, поэтому клики на моках не попадают в
  аналитику музея.

## Архитектура

```
app/ (страницы)  ──►  components/  ──►  lib/api/hooks.ts, admin-hooks.ts   (TanStack Query)
                                           │
                                           ▼
                                   lib/api/endpoints.ts, admin.ts, analytics.ts
                                   (wire snake_case  ⇄  domain camelCase)
                                           │
                                           ▼
                                   lib/api/client.ts  request() / fetchAllPaged()
                                           │
                        ┌──────────────────┴──────────────────┐
                        ▼                                     ▼
       MSW (mocks/, при USE_MOCKS=true)        backend (Yandex API Gateway)
```

- **Всё рендерится на клиенте.** Страницы — тонкие обёртки над `*-view.tsx` с
  `"use client"`, данные грузятся через React Query в браузере. SSR с данными не
  используется.
- **Два слоя типов.** Wire-типы (`WireHall`, `WireExhibit`…) описаны вручную по
  OpenAPI backend и живут только в `lib/api/*`. Мапперы (`mapHall`, `mapExhibit`…)
  сразу переводят ответ в доменные типы из `lib/types/`. UI не знает про
  snake_case. Кодогенерации нет: при изменении контракта правьте wire-тип и
  маппер руками.
- **`request()`** (`lib/api/client.ts`) — единственная точка выхода в сеть.
  Он сериализует JSON, добавляет query-параметры, ставит таймаут 15 с и
  подставляет `Authorization: Bearer` ко всем путям `/admin*`. На не-2xx бросает
  `ApiError(status, body)`. `requestFile()` скачивает бинарные выгрузки
  аналитики, `fetchAllPaged()` дочитывает постраничные списки (backend отдаёт не
  больше 100 записей за запрос).
- **Состояние.** Серверные данные живут в кеше React Query (`staleTime` 60 с,
  1 ретрай, без рефетча по фокусу). Клиентское состояние — в Zustand: история
  чата (`lib/store/chat-store.ts`, сохраняется в `localStorage`) и плеер озвучки
  (`lib/store/audio-store.ts`).
- **Инвалидация после правок в админке.** Любая мутация сбрасывает ключи
  `halls`, `hall`, `showcase`, `exhibit` и `admin` (`lib/api/admin-hooks.ts`),
  чтобы публичные экраны сразу показывали изменения.

| `/chat`                                                     | Диалог с гидом                                    | `POST /guide/story`, `POST /guide/chat`                            |
| `/admin`                                                    | Обзор каталога                                    | —                                                                  |
| `/admin/halls`, `/admin/halls/new`, `/admin/halls/[hallId]` | Залы: список с перестановкой, редактор            | `/admin/halls*`                                                    |

## Подсистемы

### Каталог: залы, витрины, экспонаты

- `hall.id` **не равен** `hall.hallNumber`. Например, Голубая гостиная —
  зал №8, но `id=14`. В подписях всегда используйте номер (`hallTitle()` в
  `lib/labels.ts`), в ссылках — `id`.
- Номера бывают `null`. Зал «Вне постоянной экспозиции» не имеет номера, а
  витрина с `showcaseNumber: null` означает группу «Не в витринах» (одна на
  зал). Счётчик залов на главной учитывает только пронумерованные залы.
- Служебные залы (`isService`) backend не отдаёт в публичном `GET /halls`.
  Админка запрашивает их через `includeService: true`.
- Экспонаты зала дочитываются целиком через `fetchAllPaged` (в Аванзале их
  больше 250) и сортируются `byExhibitNumber`: по номеру как по числу, записи
  без номера идут в конец.
- Описание зала сворачивается до превью (`ExpandableText`). Превью присылает
  backend (`description_preview` / `description_has_more`); если полей нет,
  текст обрезается на клиенте. Абзацы сохраняются через `whitespace-pre-line`.

### Карточка экспоната

- Состав и порядок полей согласованы с музеем по макету (пункт I-2 фидбэка
  31.08.2026). Не переставляйте поля без согласования.
- `yearCreated` — **строка**: «1899–1903», «конец XIX века», «около 1900». Не
  приводите её к числу.
- «Фирма и мастер» — **одна строка** из `maker.text` (фолбэк — `master_name`).
  В базе это одно поле со словами-маркерами («Фирма К. Фаберже, мастер
  М. Перхин»). Разобранные `maker.firm` / `maker.master` backend тоже отдаёт, но
  разделять ли их на экране — открытый вопрос к музею.
- «Дата создания» склеивает `yearCreated` и `originPlace` в одну строку, как на
  макете музея.
- «Расположение» берётся из готовой строки backend (`locationText`). Если её
  нет, `exhibitLocation()` собирает строку сама, дословно в формате backend
  (`app/services/location.py`). Меняйте формат только вместе с backend, иначе у
  посетителя будут две разные формулировки.

### Распознавание по фото

1. `useCamera` запрашивает `getUserMedia` **только** по действию посетителя
   или если доступ уже выдан. Запрос прав при открытии экрана был багом
   (§8 баг-репорта 06.08).
2. Снимок ужимается `compressImage` (до 2000 px и меньше 2,5 МБ) и уходит в
   `POST /recognition`.
3. Backend всегда отдаёт ранжированный список `candidates`, и первый элемент —
   сам найденный экспонат. Экран «Найдено» показывает экспонат и блок «Или,
   может быть, это» (`components/recognize/candidate-list.tsx`), исключив из
   него найденный предмет по `labelSlug`. При неудаче тот же компонент
   показывает «Возможно, это».
4. Если у кандидата нет `exhibitId` (карточки нет в каталоге), ссылка ведёт в
   чат по слагу: `/chat?label=<slug>`.

### Чат с ИИ-гидом

- **Тред один на браузер.** История хранится только на клиенте:
  `localStorage`, ключ `museum-chat-history`. Ручки чтения истории на backend
  нет. «Начать заново» очищает тред (с подтверждением).
- **Контекст.** Чат открывается с контекстом из URL: `/chat?exhibit=42`,
  `?hall=3`, `?label=<slug>`. Контекст переносится в стор, для экспоната
  параллельно запрашиваются карточка (для плашки) и рассказ `POST /guide/story`,
  после чего query чистится через `router.replace("/chat")`, чтобы reload не
  плодил рассказы.
- **Семантика поля `context` в `POST /guide/chat`** (договорённость с backend
  от 28.07.2026):
  - поле отсутствует — продолжить с контекстом, который держит серверная сессия;
  - `context: {…}` — установить новый контекст;
  - `context: {}` или `null` — сбросить контекст.

  Фронт шлёт `context`, **только когда он изменился** (`sentContext` в
  `chat-store.ts`). Раньше поле уходило в каждой реплике и сбрасывало сессию,
  из-за чего пропадали подсказки (II-7).

- Общий чат с главной сбрасывает контекст прошлого зала. Иначе на общий вопрос
  гид отвечает «в материалах о зале такого нет».
- Под ответом рисуются подсказки-вопросы, «Упомянуто в ответе»
  (`referenced_exhibits`), список залов (`referenced_halls`) и плашка
  «где находится» (`location`).

### Озвучка

`useAudioStore.toggle(key, text)` запрашивает `POST /speech`, кеширует URL
аудио по ключу и держит один активный плеер на всё приложение. Ключ —
`exhibit_<id>` для карточки или `id` сообщения в чате. Первое воспроизведение
отправляет событие `tts_play`.

### QR-ссылки и онбординг

- Главная понимает `/?hall=<id>` и `/?exhibit=<id>` и сразу перенаправляет на
  зал или экспонат. **Такие QR-коды уже напечатаны** — не ломайте эти параметры.
- Для аналитики есть `?src=<точка входа>` и `?qr=<id QR-кода>`: они уходят в
  событие `app_open`.
- `?type=permanent|temporary` фильтрует залы на главной.
- «Назад» реализован через `useSafeBack`: если страница первая во вкладке
  (открыта по QR), кнопка ведёт на главную, а не за пределы приложения.
- При первом заходе без QR показывается тур по кнопкам (`CoachMarkTour`).
  Флаг `museum-tour-seen` хранится в `localStorage`.

### Админка

- **Вход:** `POST /admin/login {username, password}` → Bearer-токен. Токен
  хранится в `localStorage` и восстанавливается при перезагрузке
  (`lib/api/admin.ts`, `components/admin/auth-gate.tsx`). Логин и пароль от
  прода выдаёт владелец backend, в репозитории их нет.
- **CRUD** идёт через `/admin/*`. Голые `/halls`, `/showcases`, `/exhibits` —
  только чтение.
- **Форма экспоната открывается на полной карточке** `GET /admin/exhibits/{id}`,
  а не на строке публичного списка. В строке списка нет части полей (материал,
  описание, история), и сохранение затирало их `null` (IV-1).
- **PATCH отправляет только изменённые поля** (`exhibitPatchToWire` сравнивает с
  карточкой, на которой открыли форму). Если ничего не изменилось, запрос не
  уходит.
- **Фото:** галерея экспоната (`/admin/exhibits/{id}/media`, флаг
  `is_primary` делает фото главным) и обложка зала (`/admin/halls/{id}/cover`).
  Перед загрузкой фото сжимается, см. [подводные камни](#инварианты-и-подводные-камни).
- **Удаление** непустого зала или витрины backend отклоняет с 409.
  `?force=true` фронт намеренно не шлёт: каскадное удаление каталога из
  админки не нужно.
- **Порядок залов** меняется перетаскиванием (`PUT /admin/halls/reorder`).
  Можно отправлять подсписок: backend переставляет залы по слотам.
- В форме зала есть переключатели «Служебная запись» (`is_service`) и
  «Временная выставка» (`is_temporary`).

### Телеметрия и аналитика

Посетитель анонимен. Фронт копит события в очереди (`lib/telemetry/tracker.ts`)
и отправляет пачками в `POST /telemetry/events`:

- пауза 3 с склеивает всплеск событий в одну пачку, в пачке не больше 50
  событий (иначе backend вернёт 422), очередь не длиннее 200 событий (старые
  выбрасываются);
- последняя пачка уходит на `visibilitychange` через `navigator.sendBeacon`:
  на телефонах `beforeunload` часто не срабатывает;
- `session_id` хранится в `sessionStorage` и рвётся после 30 минут тишины (как
  `SESSION_TIMEOUT_MINUTES` на backend), `device_id` — в `localStorage`. Оба —
  случайные UUID, без фингерпринтинга.

Типы событий: `app_open`, `hall_view`, `showcase_view`, `exhibit_view`,
`recognition`, `chat_open`, `chat_message`, `tts_play`, `search_query`,
`session_end`. Источник перехода на карточку (`hall`, `search`, `recognition`…)
кладётся в `sessionStorage` на секунды через `markExhibitSource()` перед
кликом по ссылке.

Раздел «Аналитика» в админке читает `/admin/analytics/*`: плитки с
подсказками к метрикам, частые вопросы, вопросы без ответа, маршруты,
экспонаты, качество распознавания. Период задаётся фильтром. Выгрузка — `.xlsx`
или `.pdf`, по одному отчёту или весь отчёт одним файлом. Определения метрик
лежат в backend: `docs/analytics-metrics.md`.

## Дизайн-система

Стиль — **строгий музейный, без скруглений**, по мотивам fabergemuseum.ru. Это
осознанное решение, не недосмотр.

- Токены — в `app/globals.css` (`@theme`, Tailwind v4). Все `--radius-*` равны
  `0`. Не добавляйте `rounded-*`, кроме `rounded-full` для точек и аватаров.
- Палитра: белый фон, почти чёрный текст `#0a0a0a`, тёплый бежевый `#f5f4f0`,
  рамки `#e5e2dc`, золотистый акцент `#8b6f3f` для главных действий.
- Шрифты: Inter (текст) и Playfair Display (заголовки, класс `font-display`),
  оба с кириллицей через `next/font/google`.
- Заголовки и меню — Title Case, не сплошной uppercase. Uppercase с
  разрядкой используется только для мелких подписей секций.
- **Кольцо фокуса отключено сознательно** (`outline: none` в `globals.css`).
  Фокус у полей ввода показывает затемнение рамки (`focus-within:border-foreground`).
  Это решение владельца продукта; мы понимаем, что оно ухудшает доступность с
  клавиатуры.
- Классы склеиваются через `cn()` (`clsx` + `tailwind-merge`). Иконки —
  `lucide-react`. Новые примитивы кладите в `components/ui/`.

## Сборка и деплой

```bash
npm run build
npm run start            # или: npm run start -- -p 3100
```

- **Нужен Node-сервер (`next start`), статический экспорт не работает.**
  `generateStaticParams` в `halls/`, `showcases/` и `exhibits/` берёт ID из
  моков: эти страницы собираются заранее, а остальные ID рендерятся по запросу.
  `output: "export"` потребовал бы перечислить при сборке все ID живой базы (см.
  комментарий в `next.config.ts`).
- Картинки не оптимизируются Next (`images.unoptimized: true`). Допустимые хосты
  картинок перечислены в `next.config.ts` (`remotePatterns`); новый CDN нужно
  добавить туда.
- `NEXT_PUBLIC_*` задаются на этапе сборки.

## Инварианты и подводные камни

Короткий список того, что уже ломалось или сломается при невнимательной правке.

**Данные и контракт**

1. `hall.id` ≠ `hall.hallNumber`. Номер — для людей, `id` — для ссылок.
2. `hallNumber` и `showcaseNumber` бывают `null`, и это не ошибка данных.
3. `yearCreated` — строка. Любой `Number()` по ней портит датировки.
4. Форма экспоната в админке работает только на полной карточке из
   `GET /admin/exhibits/{id}`, а PATCH шлёт только изменённые поля. Отступление
   от любого из двух правил затирает поля на проде.
5. `context` в `/guide/chat`: отсутствие поля и `{}` означают разное (см.
   [«Чат с ИИ-гидом»](#чат-с-ии-гидом)).
6. Списки дочитываются через `fetchAllPaged`. Один `request()` вернёт не больше
   100 записей.
7. Контракт wire-типов написан вручную. Сверять его нужно с `openapi.yaml` и
   кодом `app/routers/*.py` из `origin/main` backend, а не с локальным клоном,
   который мог отстать.

**Платформа**

8. **Лимит загрузки ~3,5 МБ ставит Yandex API Gateway, а не backend.** Больший
   запрос шлюз обрывает без CORS-заголовков, и браузер показывает «Failed to
   fetch» вместо 413. Поэтому любое фото перед отправкой проходит через
   `compressImage` (`lib/image.ts`): и в `/recognition`, и в админке.
9. **Полная перезагрузка страницы при переходе по `<Link>` бывает только в
   dev** (Turbopack + `trailingSlash`). В production-сборке навигация
   клиентская. Не делайте выводов о поведении приложения по dev-режиму.
   Комментарий в `lib/telemetry/index.ts` написан до того, как это выяснилось.
10. В dev React StrictMode запускает эффекты дважды. Телеметрия защищена от
    двойной отправки через `useRef` (`useTrackView`) — сохраняйте это в новых
    событиях, иначе аналитика задвоится.
11. `crypto.randomUUID` доступен только в защищённом контексте. На http-стенде
    работает фолбэк в `tracker.ts`.
12. API Gateway иногда флапает на деплое backend: случайные 404 или устаревшие
    данные. Прежде чем чинить фронт, перезапросите данные.

**UI**

13. QR-параметры `/?hall=` и `/?exhibit=` уже напечатаны на табличках в музее.
14. Скругления и кольца фокуса отключены намеренно (см. [«Дизайн-система»](#дизайн-система)).

## Процесс и история решений

- **Откуда задачи.** Их ставит заказчик (музей и продукт) в виде ТЗ и
  баг-репортов с нумерованными пунктами (§3, I-2, II-7, IV-1…). Номера пунктов
  стоят в коммитах и комментариях. Если непонятно, зачем написана строка,
  ищите по номеру в `git log` и в `docs/` backend-репозитория: там лежат
  сводные ответы по баг-репортам (`bugreport-2026-08-12-answers.md`,
  `bugreport-2026-08-31-answers.md` и др.).
- **Git.** Одна задача — одна ветка (`feat/…`, `fix/…`, `docs/…`) от `main`,
  затем PR в `main`. Одна логическая правка — один коммит.
- **Сообщения коммитов** — в стиле Conventional Commits, текст на русском:
  `fix(admin): PATCH экспоната шлёт только изменённые поля, фото не затирается (IV-1)`.
- **Комментарии** пишутся по-русски и объясняют **почему**, часто со ссылкой на
  пункт баг-репорта и дату.
- **Граница с backend.** Если баг на стороне backend, не правьте его из фронта
  обходом: заведите задачу в backend-репозитории с репро, ожиданием и
  ссылками на код. Фронтовую часть и моки делайте сами.
- **Данные каталога** (атрибуции, датировки, витрины) правятся через админку
  или скриптами backend с файлом отката, а не во фронте.
